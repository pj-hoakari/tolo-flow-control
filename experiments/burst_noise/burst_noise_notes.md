# バースト方式の観測の揺れと急増判定の振る舞い

調査日: 2026-11-06

バースト方式のカメラ（数枚を撮って送る観測点）では、撮影の周期によって流量とエリア内検知人数が偶然で揺れる。
本書はこの揺れを flow-control の実際のコードに通したときの判定と出力の変化と、現行の急増判定の振る舞いを記録する。
数値はすべてシミュレーションで求めた。実際の映像では確かめていない。

## 結論

- 揺れは急増、停滞警戒、組合せ発火の判定をほとんど変えなかった。一定の流れで誤って成立した回は、流量 3 通り × 周期 3 通り × 各 2 時間 × 20 回で 0 だった。
- 今回値を使う処理の出力は、周期とともに揺れた。devtools の 9 シナリオで、需要の差の中央値は周期 3 秒で 0〜7%、10 秒で 0〜20% だった（school-north-stair-peak を除く）。
- school-north-stair-peak は、約 1% の揺れでも需要が 3% 動いた。ほかのシナリオは 0〜1% だった。
- 揺れを減らすために今回値を直近の平均にすると、流量が増えている途中で今回値が遅れた。揺れがなくても需要が最大 26% ずれた。
- 現行の急増判定は閾値 10%/分では 15 分で 4 倍になる増え方でも 3 倍の段差でも成立しなかった。傾き ÷ 窓の平均には、増え方によらない上限 6/W（W = 30.5 分で約 19.7%/分）がある。
- 現行の定式で閾値を 5%/分にすると、一定の流れでの誤った成立は 0 のまま、15 分で 4 倍になる増え方で約 13 分、3 倍の段差で約 7〜8.5 分に成立した。

## 揺れのモデル

揺れの大きさは tolo-walk-calibration-poc のシミュレーション（帯 5 m、5 枚 × 200 ms、4 隅の方式、PoC の `estimateBurst`、理想の追跡）で、30 秒の計測と 1 分の窓ごとに推定と真の値を比べて求めた。

| 値                                    | 相対誤差         | 周期 3 / 5 / 10 秒の係数 |
| ------------------------------------- | ---------------- | ------------------------ |
| 30 秒の計測の流量                     | c ÷ √(人/分)     | 0.55 / 0.79 / 1.72       |
| 30 秒の計測のエリア内検知人数         | d ÷ √(平均人数)  | 0.094 / 0.16 / 0.42      |
| 1 分の窓の流量（devtools のシナリオ） | c ÷ √(人/分)     | 0.35 / 0.50 / 1.17       |
| 1 分の窓のエリア内検知人数            | d ÷ √(平均人数)  | 0.068 / 0.10 / 0.28      |

係数は毎分 5、18、90 人の流れでほぼ同じ値になった。誤差の分布はほぼ左右対称だった（歪度 −0.22〜0.39）ので、正規分布で与えた。
tolo-observation（origin/main）は計測が届くたびに観測サイクルを回し、直近 1 分の窓（`OBSERVATION_WINDOW` の既定）で流量（人/分）とエリア内検知人数（窓の中の平均）を作る。履歴は直近 30 分のスナップショットである。
`detection_noise.py` はこの形をまねて、30 秒の計測ごとに独立な誤差を与え、隣り合う 2 つの計測から 1 分の窓の値を作る。

## 実験

| スクリプト             | 内容                                                                                                                                                                | 結果                            |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------- |
| `detection_noise.py`   | devtools の venue グラフで、時間を 30 秒ずつ進めて `detect()` を呼ぶ。前の結果の状態を次に渡す。4 時間の履歴で P90 と基準停滞量を作り、その後の 120 分を判定する     | `results/detection_noise.md`    |
| `downstream_noise.py`  | `experiments/degraded_operation` の 9 シナリオの観測値と履歴の各点に揺れを加え、`run_pipeline` の判定、需要、通過量、通行制限の上限値を揺れのない場合と比べる。30 回ずつ | `results/downstream_noise.md`   |
| `surge_formulation.py` | `detection_noise.py` と同じ点列で、急増の定式 5 通りの値を 30 秒ごとに計算し、閾値ごとに成立を比べる                                                                 | `results/surge_formulation.md`  |

どれも本番の設定（tolo-observation の defaultFlowConfig）で動かした。
真の流量は 30 秒ごとの Poisson で、エリア内検知人数は通過数 × 帯の通過時間（5 m ÷ 1.2 m/s）に立ち止まる人を足した値である。

```sh
uv run python experiments/burst_noise/detection_noise.py
uv run python experiments/burst_noise/downstream_noise.py
uv run python experiments/burst_noise/surge_formulation.py
```

### 場面

注目する辺の流量とエリア内検知人数を、40 分から次のように変える。

| 場面       | 変化                                                              |
| ---------- | ----------------------------------------------------------------- |
| steady     | 変わらない                                                        |
| surge      | 流量が毎分 15% の指数で増え、20 倍で止まる                        |
| ramp4      | 流量が 15 分で 4 倍まで直線で増え、そのまま                       |
| step3      | 流量が 3 倍に上がり、そのまま                                     |
| diurnal    | 流量が 120 分で 4 倍まで直線で増える                              |
| recover    | 流量が 10 分だけ 0.3 倍に下がり、もとに戻る                       |
| stagnation | 5 分で立ち止まる人が増え、エリア内検知人数が基準の 3 倍ほど上がる |
| combined   | surge と stagnation を同時に起こす                                |

流量は毎分 5、18、90 人、撮り方は連続観測と周期 3、5、10 秒である。
`detection_noise.py` は steady、surge、ramp4、stagnation、combined を、手当て「なし」と「Observation が 3 分の移動平均を送る」の 2 通りで試す。`surge_formulation.py` は steady、surge、ramp4、step3、diurnal、recover を試す。

## 揺れと判定

| 周期                                       | 3 秒        | 5 秒        | 10 秒                |
| ------------------------------------------ | ----------- | ----------- | -------------------- |
| 一定の流れでの誤った成立                   | 0           | 0           | 0                    |
| 急増と発火の成立の遅れ（連続観測との差）   | 0.5 分以内  | 0.5 分以内  | 0.75 分以内          |
| 停滞警戒の成立の遅れ（連続観測との差）     | 0.75 分以内 | 1.5 分以内  | 2.5 分以内           |
| 発火の見逃し（毎分 5 人、20 回中）         | 0           | 0           | 1〜2（連続観測は 0） |

遅れの差は場面と流量の組ごとの中央値の差のうち最大のものである。
surge の場面では、急増は始まりから約 18〜19 分で成立した。
Observation が 3 分の移動平均を送ると、急増、停滞警戒、発火の成立が約 0.75〜1.5 分遅れた。

## 揺れと今回値を使う処理

| 周期  | 需要の差（中央値） | 通行制限の上限値の差（中央値） |
| ----- | ------------------ | ------------------------------ |
| 3 秒  | 0〜7%              | 0〜2%                          |
| 5 秒  | 0〜9%              | 0〜4%                          |
| 10 秒 | 0〜20%             | 0〜5%                          |

school-north-stair-peak を除く 8 シナリオの範囲である。school-north-stair-peak は周期 3 秒で 36%、10 秒で 77% だった。
1 回のスナップショットでは、expo-incident-resume と school-north-stair-peak で発火しなくなる回があった（周期 10 秒で 30 回中 10〜17 回）。

### 今回値を平均にする手当て

`downstream_noise.py` の `obs_ma3` は Observation が 3 点の移動平均を送る形、`fc_mean3` は flow-control が今回値を直近 3 点の平均にする形である。
devtools のシナリオの多くは、履歴の最後の点（1 分前）より今回値のほうが大きい、流量が増えている途中のものである。

| 揺れのない場合 | 需要の差 | 通過量の差 | 通行制限の上限値の差 |
| -------------- | -------- | ---------- | -------------------- |
| `obs_ma3`      | 0〜26%   | 0〜22%     | 12〜14%              |
| `fc_mean3`     | 0〜26%   | 0〜22%     | 0%                   |

窓の幅が同じなら、2 つの形の今回値は同じ値になる。`obs_ma3` は履歴の点列もならすので、通行制限の上限値が変わった。
揺れのある場合、需要の差の中央値は周期 3 秒と 5 秒では 8 シナリオ中 7〜8 で手当てなしより大きかった。周期 10 秒では 4〜5 で大きく、2 で小さかった。

## 急増判定の振る舞い

数理 v0 §9.1 の急増は直近 W 分（W = 30 + 観測分解能）の流量の点列と今回値に最小二乗で傾き β を当て、β ÷ 点列の平均 × 100 を閾値 `surge_rate_threshold_percent_per_min`（tolo-observation の既定は 10）と比べる。

### 上限

窓の中の流量を f(x)（0 ≤ x ≤ W）とすると、

```latex
\frac{\beta}{\bar f} = \frac{12}{W^2}\cdot\frac{\int_0^W (x - W/2)\, f(x)\, dx}{\int_0^W f(x)\, dx} \le \frac{6}{W}
```

となる。右の比は流量の重心が窓の中央からどれだけ終わりに寄っているかで、終わりに集まるほど 6/W に近づく。
W = 30.5 分なら上限は約 19.7%/分で、閾値 10%/分は流量の重心が窓の終わりから約 7.5 分以内に入ることを求める。

## 前提と限界

- 追跡は理想（人を取り違えない）とした。BYTETracker の既定の設定では、遅く混んだ流れで ID を取り違え、流量が約 1.2 倍に出る（tolo-walk-calibration-poc の `docs/burst-cadence-check.md`）。混み具合で倍率が変わるこの偏りは、ここでは入っていない。
- 人どうしの重なり（混雑での検出漏れ）は入っていない。diurnal 以外の日内の流量の変化も入っていない。
- 立ち止まる人はエリア内検知人数に揺れなしで足した。
- `downstream_noise.py` は devtools のシナリオだけで、点の間隔は 1 分である。シナリオの多くは流量が増えている途中を切り取っている。
- 1 回のスナップショットで判定が変わっても、実際の運用では 30 秒後のサイクルで評価し直される。
